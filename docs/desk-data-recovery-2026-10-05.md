# Desk Map 数据恢复即时更新（2026-10-05）

范围：S1/S3 现有决策与报告事实出口；Phase 6 冻结运行时生产故障修复。

## 问题与修复

Core 持续刷新策略决策，但桌图源按 15 分钟刷新，Rust 报告只在整点、
半点窗口接受一次桌图。已推送的“报价未齐／概率不可估”即使恢复，也可能
继续等待下一个固定时刻。

Core 保存最终决策和市场帧后，比较最近桌图已展示的数据能力。新鲜数据恢复时，
复用现有报告构建函数单次读取当前数据和已提交决策，重新检查决策与报价年龄，
生成带当前时间的“数据恢复更新”。不重跑另一套策略、不做图片、模型请求或重试睡眠。
10 点翼、20 点翼报价与各自概率单独识别；OI 尚未验证不会阻止铁鹰数据恢复更新。

Python 仍是最终交易决策 owner。恢复只是新的事实摘要，不等于入场授权，
不改变选腿、贷记、风险、provider、新鲜度或交易门槛。

## 现有链路与去重

复用 `desk_map_projection.v1`，仅增加可缺省的 `recovery_seen`、`recovery_of`：

- `recovery_seen` 是本轮半小时桌图之后已经公告的数据能力集合，不代表当前交易权限。
  半小时桌图建立新基线；15/45 分钟纯存档继承基线，不能吃掉尚未推送的恢复。
  Persistent timer 迟到补跑也不能消费恢复，复用现有两分钟源启动宽限。
  两种翼宽交替暂缺、恢复不会形成无限补发。
- `recovery_of` 引用被更新的桌图 ID。锁内比较当前 ID，避免覆盖并发发布的新桌图。
- 恢复摘要有效期两分钟；发送前检查当前 session、交易日、时间与有效期。
- Rust 报告跳过半小时等待与模型改写，使用现有已验证消息；现有 ledger 以
  `recovery:<projection_id>` 去重，进程重启后也不重发同一更新。
- 定时桌图仍按原计划发布，健康检查独立记录定时报告时间，恢复补发不能掩盖定时故障。

没有新服务、timer、数据库、表、队列、依赖、配置开关或 wire 版本；未修改 Bark
传输代码、配置与目标，仍使用既有投递路径。数据恢复消息是用户本次授权的补发。

## 验收与运行边界

回归覆盖 GTH/RTH 非定时窗口、部分恢复、报价年龄、未来/过期决策、
并发桌图、交替缺失、重启去重，以及恢复消息不能遮蔽定时故障。

发布前检查：Python 全量 3,530 项通过（2 个既有依赖弃用提示），Rust workspace
312 项通过，Ruff、Import Linter、Cargo fmt/Clippy 和 diff 检查通过。
Core/Bridge/Report release 构建及四个实际运行配置检查通过。现场一次单次
桌图准备测得 3.811 秒；它不是端到端投递延迟。

复杂度：生产文件新增/删除 0/0，7 个现有生产文件净增 220 行；依赖、配置键、
服务/timer、数据库/表均新增/删除 0/0。没有删除 owner 或旧定时路径，恢复消息
复用原持久化/投递实现，取消其等待固定时刻和模型写手的条件。

实际延迟取决于 Core 周期、一次报告准备和既有桥接/投递轮询；不承诺零延迟。
如果券商没有提供合格的 exact 四腿报价或 Greeks，本修复不能制造报价或胜率。
概率沿用现有历史模拟频率及其未校准标记，不表示新增收益验证。

部署必须先升级接收可选字段的 Rust Core/Bridge/Report，再重启 Python Core，
恢复桌图 timer；仍使用现有 owner 与配置。回滚时同样先暂停 Python 发布端，
回退投影/health 的新增可选元数据后再恢复旧的严格 Rust reader。
