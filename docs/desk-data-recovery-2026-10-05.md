## 问题与修复

Core 持续刷新策略决策，但桌图源按 15 分钟刷新，Rust 报告只在整点、
半点窗口接受一次桌图。已推送的“报价未齐／概率不可估”即使恢复，也可能
继续等待下一个固定时刻。

Core 保存最终决策和市场帧后，比较最近桌图已展示的数据能力。新鲜数据恢复时，
复用现有报告构建函数单次读取当前数据和已提交决策，重新检查决策与报价年龄，
生成带当前时间的“数据恢复更新”。不重跑另一套策略、不做图片、模型请求或重试睡眠。
10 点翼、20 点翼报价与各自概率单独识别；OI 尚未验证不会阻止铁鹰数据恢复更新。

Python 仍是最终交易决策 owner。恢复只是新的事实摘要，不等于入场授权，
不改变选腿、贷记、风险、provider、新鲜度或交易门槛。

## 现有链路与去重

复用 `desk_map_projection.v1`，仅增加可缺省的 `recovery_seen`、`recovery_of`：

- `recovery_seen` 是本轮半小时桌图之后已经公告的数据能力集合，不代表当前交易权限。
  半小时桌图建立新基线；15/45 分钟纯存档继承基线，不能吃掉尚未推送的恢复。
  Persistent timer 迟到补跑也不能消费恢复，复用现有两分钟源启动宽限。
  两种翼宽交替暂缺、恢复不会形成无限补发。
- `recovery_of` 引用被更新的桌图 ID。锁内比较当前 ID，避免覆盖并发发布的新桌图。
- 恢复摘要有效期两分钟；发送前检查当前 session、交易日、时间与有效期。
- Rust 报告跳过半小时等待与模型改写，使用现有已验证消息；现有 ledger 以
  `recovery:<projection_id>` 去重，进程重启后也不重发同一更新。
- 定时桌图仍按原计划发布，健康检查独立记录定时报告时间，恢复补发不能掩盖定时故障。
